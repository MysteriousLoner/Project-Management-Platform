<!-- managed-by: techmation-project-knowledge -->

Use the `techmationKnowledge` MCP connection. Derive the employee from `identity.me`; never supply another employee as the author.

1. Resolve the canonical Git remote with `projects.resolve`. If unmatched, ask once to select an existing project or create one in an employee department, then `projects.bind` with a new idempotency key. Keep the project ID in `.codex/techmation-project.json` if no Git remote exists; ask for the existing project when this local association is absent. Never upload remote URL credentials.
2. Find the installed `collect-project-evidence.mjs` next to this skill. Run `node <helper-path> --identity --cwd <project-root>` to obtain this machine's stable client ID and Git author email. Query `progress.get_context` with project ID and client ID. A missing checkpoint requires asking for the first collection date; suggest the current Monday in Asia/Kuala_Lumpur. Preserve that baseline afterward.
3. Save the returned context as a temporary local JSON file. Run `node <helper-path> --cwd <project-root> --context <file> --baseline-date YYYY-MM-DD`. The helper reads only matching local project conversations and local Git metadata; its output stays local. Inspect current code/diffs where needed to verify the work. Do not read hidden reasoning or unrelated chats. Do not claim that unavailable or cloud-only history was inspected.
4. Group corroborating conversation, commit, and working-tree evidence into concise accomplishments by actual Malaysia work date. Distinguish completed from in-progress work. Compare with `recentProgress`; exclude previously reported facts and other employees' work. Evidence IDs must be the stable IDs emitted by the helper. Paths/ticket references can support a claim but must not replace its unique change evidence. For uncertain attribution or dates, ask rather than inventing them.
5. Submit only new evidence-backed summaries, explicit corrections, and new/changed external blockers with `progress.submit`. A correction references `supersedesId`; do not resubmit a previous entry as new. External blockers require an outside party and action needed. Reuse the existing blocker key and set `expectedEventId` to its current event ID. Resolve only with evidence or an explicit employee statement; absence is not resolution.
6. Pass the helper's consumed source checkpoints, the context's expected checkpoint revision, baseline date, and collection gaps. Do not advance sources the helper could not read. If `hasMore` is true, submit this batch and repeat from fresh server context until drained. A batch with no accomplishments can still record successfully inspected sources, using empty entries/blockers. `CHECKPOINT_CHANGED` or `BLOCKER_CHANGED` requires reloading context and reconciling; do not overwrite a newer checkpoint.
7. Generate one idempotency key for each exact submission. If its response is lost, retry the same payload and key. Stop after three transport retries and report the uncertain result; a later retry must retain that payload/key. Do not claim success before the server confirms it.

Exclude credentials, raw conversations, complete source files, and hidden reasoning from submissions. Summarize what was saved, the covered period, duplicates skipped, and collection gaps. Keep helper/context files outside Git and remove temporary context files when finished. Never create commits, push code, or deploy as part of reporting progress.
